# RepoLore.Cli 1.0.0 (no author signature)

First stable release. RepoLore keeps a repository's operational memory as Markdown under `_repolore/`, and the `repolore` command reads it, checks it and protects it with local checkpoints, without any network access.

## Install

```text
dotnet new tool-manifest
dotnet tool install RepoLore.Cli --version 1.0.0 --local
```

A .NET 10 SDK is needed to install and a .NET 10.0.x runtime to run. See the [user guide](../user-guide.md).

## Upgrading

- **From a 1.0.0 release candidate:** change the version in `.config/dotnet-tools.json` and run `dotnet tool restore`. The knowledge format and the history are unchanged. From `1.0.0-rc.1`, run `repolore init --update-method` if you want the current method text, and check that no `.repoloreignore` or `history.exclude` rule ends with a space: such a rule is now refused, and in `history.exclude` it blocks writes until you remove the space.
- **From `0.1.0-preview.1`:** the same, and rename a `_repoloreignore` file to `.repoloreignore`.

## What stays stable in 1.x

Scripts and agents can rely on these until a 2.0:

- the exit codes (`0` success, `1` findings, `2` usage, `3` failure) and the finding and error IDs;
- the JSON field names and their meaning;
- the options and what they do;
- knowledge format 1 and the local history format, which every 1.x version reads;
- the behaviors pinned by the scenarios tagged `contract`: what `tree` lists and in what order, the checkpoint time format, the rule syntax, the context budget's order, and the ids that `restore`, `migrate` and `init --update-method` report.

A 1.x version may add options, JSON fields, and findings for real defects. The wording of human-readable output may change.

## Changes since 0.1.0-preview.1

The notes of the three release candidates list every change: [`1.0.0-rc.1`](1.0.0-rc.1.md), [`1.0.0-rc.2`](1.0.0-rc.2.md), [`1.0.0-rc.3`](1.0.0-rc.3.md). In short:

- **Renamed:** the source-discovery rules file is `.repoloreignore`; a leftover `_repoloreignore` is reported.
- **Recovery:** `restore`, `migrate` and `init --update-method` name the command that undoes them, and the messages for corrupt history name the way out.
- **Fixes:**
  - `init` refuses to create a knowledge base below an existing one;
  - `--explain` reports that disabled history covers nothing;
  - links written with `%20` escapes are checked correctly;
  - `--quiet` silences `path` and `tree` too;
  - `init` writes LF line endings on every operating system;
  - a file in place of `_repolore/.history` gets a clear message.
- **Settled for 1.0:**
  - `tree` lists only notes and the folders that hold them, depth first;
  - checkpoint times have six fractional digits;
  - a rule ending with whitespace is refused;
  - `migrate --check --dry-run` is a usage error;
  - `init --update-method --json` reports its checkpoint.
- **Method:** the method `init` writes covers root-relative targets, `--node` for custom areas and the context budget.
- **Documentation:** the user guide documents every option, the rule syntax, `repolore.json`, session ids, the link check and recovery from damaged history. `SECURITY.md` describes private vulnerability reporting.
- **Release files:** each release publishes a CycloneDX SBOM and a SHA-256 checksum file for the exact package and SBOM.
- **Testing:** a scenario suite replays a real user's history from an append-only reference repository on Windows, Linux and macOS in every CI run, twice a week and before each release. An autonomous field test of `1.0.0-rc.1` (57 experiments) found the issues fixed in the later candidates.

## Limits

- **No author signature.** NuGet.org adds only its own repository signature. Author signing is not planned for 1.0.0 (maintainer decision of 2026-10-24). This is not an enterprise-ready or certified release, and it makes no guarantee about what external editors or agents do with content they read.
- **Network evidence:** the networking-blocked run exists on Linux only, and there is no network-call trace.
- **Formats:** unknown knowledge formats are refused, and migration is explicit.

## Verify

The publish run records the SHA-256 of the exact pushed package and of its SBOM in `RepoLore.Cli.1.0.0.sha256`, which is attached to the GitHub release with the SBOM. NuGet.org adds a repository signature after upload, so a downloaded copy differs in bytes but not in content. `dotnet nuget verify` checks that signature.
