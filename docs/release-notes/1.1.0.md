# RepoLore 1.1.0 (no author signature)

RepoLore no longer needs .NET: the same tool now also ships as a native executable for Windows, Linux (glibc) and macOS, on x64 and arm64, through the package managers you may already use. The commands, their output and the knowledge format are the same as in 1.0.0.

## Install

| With | Run |
|---|---|
| macOS or Linux | `curl -fsSL https://repolore.org/install.sh \| sh` |
| Windows (PowerShell) | `irm https://repolore.org/install.ps1 \| iex` |
| Homebrew | `brew install repolore-org/tap/repolore` |
| winget | `winget install repolore` |
| Python (pipx, uv or pip) | `pipx install repolore` |
| Node.js (npm) | `npm install -g repolore-cli` |
| .NET (pinned per repository) | `dotnet tool install RepoLore.Cli --version 1.1.0 --local` |

Every channel except .NET installs the same native executable; the archives are also attached to this release. The .NET tool needs a .NET 10 SDK to install and a .NET 10.0.x runtime to run. See the [user guide](../user-guide.md).

## Upgrading

- **.NET tool:** change the version in `.config/dotnet-tools.json` to `1.1.0` and run `dotnet tool restore`. The knowledge format, the history and the method are unchanged, so there is nothing to migrate.
- **Switching to the native executable:** install it from any channel above. It reads the same `_repolore/` and the same history, so a repository can mix both. A repository that pins the .NET tool in its manifest keeps using that pin with `dotnet tool run repolore`.

Everything listed as stable in 1.x in the [1.0.0 notes](1.0.0.md) still holds.

## Changes since 1.0.0

- **New channels:** archives on the GitHub release, `repolore` on PyPI, `repolore-cli` on npm (`repolore` there is an unrelated project), `repolore-org/tap/repolore` on Homebrew, `repolore` on winget, and install scripts on repolore.org that check the archive against this release's checksums before installing it. Each executable passes the same smoke test and scenario suite as the .NET tool, on a machine of its own platform.
- **Windows output is UTF-8:** RepoLore now switches the console to UTF-8, as `dotnet tool run` already did before starting it, so a path such as `docs/équipe/` prints the same on every channel and nothing is lost to the console's code page. Only a tool started without `dotnet tool run` (a global tool, or the new executables) behaves differently than before; the console stays in UTF-8 after RepoLore exits, as it does after any `dotnet` command.
- **Release files:** the checksum file is now `repolore-1.1.0.sha256` and covers every file attached to this release. A second SBOM, `repolore-1.1.0.native.cdx.json`, lists the .NET runtime components inside the executables, and every archive carries the runtime's MIT license and notices as `THIRD-PARTY-NOTICES.txt`.
- **Publishing:** every channel is published from the same tagged commit by one workflow, run by hand with one checkbox per channel; pushing a tag no longer publishes.

## Limits

- **No author signature, no code signature.** NuGet.org adds only its own repository signature. The executables are not signed: on macOS a file downloaded with a browser is blocked until you allow it (the install script and Homebrew are not affected), and Windows SmartScreen may warn. This is not an enterprise-ready or certified release, and it makes no guarantee about what external editors or agents do with content they read.
- **Platforms:** the Linux executables are built on Ubuntu 22.04 for glibc distributions (the PyPI wheel's `manylinux` tag states the oldest glibc they accept); musl (Alpine) is not built. The macOS executables need macOS 12 or later.
- **Network evidence:** the networking-blocked run exists on Linux x64 only, and there is no network-call trace. The executables link the operating system's networking libraries because the .NET runtime does; RepoLore's code cannot call them.
- **npm:** the `repolore-cli` package starts the executable through a small Node.js launcher. That child process belongs to npm's packaging, not to RepoLore.

## Verify

Download `repolore-1.1.0.sha256` from this release and check the files you downloaded with `shasum -a 256 -c --ignore-missing repolore-1.1.0.sha256` (or `sha256sum -c --ignore-missing repolore-1.1.0.sha256`). The wheels and npm packages are listed in `repolore-1.1.0.packages.sha256`. NuGet.org adds a repository signature after upload, so a package downloaded from it differs in bytes from the pushed file; `dotnet nuget verify` checks that signature.
